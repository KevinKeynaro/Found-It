## 1. Executive Summary

Found It! is a lost & found web application for a school environment, built on a **two-tier, separately managed architecture** (not a managed monorepo):

| Layer | Primary technology | Maturity status |
|---|---|---|
| Frontend | Next.js 16 (App Router) + React 19 + Tailwind CSS 4 | Official `create-next-app` scaffold, ready for development |
| Backend | Node.js + Express 5 (REST API) | **Skeleton stage only** — cannot be run yet |
| Database | MySQL (via `mysql2`) — Prisma claimed in docs | **Not installed & self-contradictory** |
| Media storage | Cloudinary | Installed, not yet used |
| Auth | JWT + bcrypt, 3-role RBAC | Installed, middleware still empty |
| DevOps | — | No CI/CD, Docker, or tests |

**Bottom line:** the frontend foundation is modern and solid, while the backend is still far from runnable. There are **3 blocking findings** (see §7) that must be resolved before any feature can be tested end-to-end.

### 4.4 Module system inconsistency (ESM vs CJS)

This is a significant finding. Three different styles coexist in the same project:

| File | Style | Problem |
|---|---|---|
| `package.json` | `"type": "commonjs"` | Sets the CJS default |
| `src/app.js` | `import express from "express"` (ESM) | Will fail to run as CJS |
| `src/db/index.js` | `import` + top-level `await` (ESM) | Top-level `await` is invalid in CJS |
| `src/controllers/users.controller.js` | `require("bcrypt")` (CJS) | Consistent with `type`, but different from the two files above |

This combination makes the backend **module-inconsistent and likely to error on start**. One decision is needed: move to ESM (`"type": "module"`) or stay on CJS and convert all `import` statements to `require`. Given Express 5 and Node 24, ESM is the more future-proof choice.

## 5. Database & Storage

There is a **contradiction between the documentation and the actual code**:

| Aspect | Claimed in `backend/README.md` | Reality in the repo |
|---|---|---|
| Driver/ORM | "MySQL with **Prisma ORM**" | `src/db/index.js` uses `mysql2/promise` (raw pool) |
| Setup commands | `npx prisma migrate dev`, `npx prisma db seed` | No `prisma/` dir, no `schema.prisma`, `prisma` not installed |
| Dependencies | Prisma as a dependency | `mysql2` is **absent from `package.json`** and **not installed in `node_modules`** |
| Data model | User, Item, Claim (fully documented) | No schema definition exists yet |

**Impact:** `src/db/index.js` will fail on `import mysql from 'mysql2/promise'` because the module is missing. This is a **blocking issue** that must be decided first: raw `mysql2` (as the code implies) or Prisma (as the docs imply). If Prisma is chosen, `src/db/index.js` must be rewritten and the `README` is already correct; if `mysql2` is chosen, the `README` must be corrected and `mysql2` added as a dependency.

**Image storage:** Cloudinary is the selected option (dependency + env credentials), with Multer as the upload intermediary. No integration code exists yet. An alternative such as Supabase Storage appears to have been considered (the `SUPABASE_*` env keys) but was never decided on.

## 6. Authentication & Authorization

Designed with a clean, well-documented pattern:

- **JWT bearer token** in the `Authorization: Bearer <token>` header, issued at login (no self-registration).
- **bcrypt** for password hashing.
- **3 roles:** `admin`, `teacher`, `student`, with an explicit permission matrix in `backend/README.md` (including ownership rules: a teacher can only edit/delete their own items).
- **Planned request flow:** `route → authenticate → authorize → validate → error handler → controller`.
- **Clear state machines:** Item `FOUND → CLAIMED → RETURNED`; Claim `PENDING → APPROVED | REJECTED`.

What does not exist yet: any middleware, Zod schema, or controller. So the authorization architecture has been thought through, but is zero percent implemented.

## 7. Findings & Risks

### Blocking (must be resolved before the backend can run)

1. **`mysql2` is neither declared nor installed** — `src/db/index.js` will error immediately on import. The database layer must be decided and its dependency added.
2. **ESM/CJS mixing** — `"type": "commonjs"` collides with the `import` statements in `app.js` and `db/index.js`. One module style must be chosen.
3. **`app.js` is not yet an Express app** — there is no `express()` instantiation, no `app.listen()`, and no routes. The backend cannot be started at all.

### Important (hygiene & quality)

4. **`backend/node_modules` is committed** — 4,052 of 4,082 tracked files. This makes the repo heavy, diffs noisy, and review practically impossible. `backend/.gitignore` exists and ignores `/node_modules`, but the contents were tracked before that rule was added, so they remain tracked.
5. **Contradictory database documentation** (Prisma vs `mysql2`) — a major source of confusion for the next contributor.
6. **No `.env.example`** — even though `.gitignore` already reserves an exception for it. New developers cannot tell which variables are required.
7. **No `start` script** in the backend `package.json`, even though the `README` documents it.
8. **`nodemon` 1.19.4** is outdated for modern Node.js.
9. **No testing strategy** — the `test` script is still a placeholder, and neither side has a test framework (Jest/Vitest/Supertest).

### Minor (maintenance notes)

10. **`backend/.env` holds credentials** — safe because it is gitignored, but the values should be rotated if ever shared via chat or screenshots.
11. **`SUPABASE_*` keys without a dependency** — exploration leftovers that could mislead.
12. **Frontend metadata not customized** — still `"Create Next App"`.
13. **`.md/DESIGN/DESIGN.md` and `.md/PRD/PRD.md` are still 0 bytes** — not yet filled in.
14. **Two branches (`main`, `development`) with near-identical content**; the `development` branch is actually further ahead in removing `node_modules` from tracking. A branch workflow should be agreed on.

## 8. Recommendations

Prioritized by impact:

**Short term — make the backend runnable**
1. Settle on one module style (ESM recommended: `"type": "module"`, then convert the `require` in the controller).
2. Choose and install the database driver. If following the existing code: add `mysql2`. If following the documentation: install `prisma` and create `prisma/schema.prisma` for the User, Item, and Claim models.
3. Complete `src/app.js`: instantiate Express, add `cors`, `express.json()`, mount routers, and `app.listen` with `PORT`.
4. Implement the `authMiddleware` (JWT verification) and `adminMiddleware` (role check) plus a global error handler.

**Medium term — quality & collaboration**
5. Clean up git: remove `backend/node_modules` from tracking (`git rm -r --cached backend/node_modules`) and confirm `.gitignore` takes effect.
6. Add `backend/.env.example` and a `start` script (`node src/app.js`).
7. Upgrade `nodemon` to `^3.x`.
8. Add testing: Vitest/Jest + Supertest on the backend, and at least lint in CI.

**Long term — product**
9. Fill in `.md/PRD/PRD.md` and `.md/DESIGN/DESIGN.md` so the API contract in `backend/README.md` has matching product and design counterparts.
10. Build out the frontend UI: login page, searchable item list, item detail, posting form for teachers, and an admin panel.
11. Consider a centralized frontend API layer (e.g. `src/lib/api.js`) plus a Next.js middleware/proxy for token handling.
12. Add CI (GitHub Actions) for lint + build on both sides, and decide on deployment targets (Vercel for the frontend, a Node/MySQL host for the backend).
